Anatomy of an
Agentic Slice

An agent is a control loop wrapped around a non-deterministic function. Every principle below is derived from that one fact — production architecture is not about making the model better, it is about making it safe to put in a loop.

Nine principles, in the order you should build them. Each is illustrated against the same reference system: a SPOT→PROBE venture-thesis agent with a faculty gate and a live human expert callback. Enterprise and student architectures do not differ in which principles apply — only in what each costs to implement.

TIER 1

The skeleton

Below this line it is not agentic, it is a chatbot with extra steps. Roughly two hours of build, and every one of the six principles that follow depends on these three.

Durable state outside the context window

The context window is a cache. The system of record is external, versioned, and reconstructed into context each turn — never the other way round.

In the reference

thesis_record v1/v2/v3 as rows in SQLite. Every turn reads the record, calls the model, writes a new version. Nothing in Tier 2 or 3 is possible without this — you cannot suspend, resume, replay or audit a run whose only memory is a transcript.

Typed contracts at every boundary

Agents pass records, not prose. Prose compounds ambiguity silently; a schema fails loudly at the boundary where you can still see it.

In the reference

SPOT emits a ThesisRecord with required fields. Faculty emits Verdict{status, objections[]} — never "I think this needs work." A Pydantic model and one retry buys the whole principle.

Bounded loops

The characteristic failure of an agent is not a crash — it is an expensive infinite loop. Every loop stops on something real: attempts, tokens, rupees, wall-clock.

In the reference

The gate revises at most three times, then escalates. Note that the $12 cap on your API key is this same principle at the outermost scope — implement the identical fence twice more inside your own code.

TIER 2

What makes it demonstrable

Three more hours. This tier is what turns a working system into one a judge can believe in without reading your source.

Tool use with provenance

Not "the model said X" but "X — from chunk 47 of document 3, quoting this sentence." Provenance is how a reader distinguishes retrieval from invention.

In the reference

PROBE writes evidence{claim, stance, source_chunk_id, quote} and the brief renders the quote inline. Fifteen lines of storage; the difference between a judge trusting the output and squinting at it.

Human-in-the-loop as a state, not an exception

An explicit state the run suspends into and resumes from — so the process can exit entirely and a later invocation picks up where it stopped.

In the reference

An assumption marked unresolvable_from_corpus suspends the run to awaiting_expert, posts a question to a real alum, and resumes on their answer — with a timeout that degrades to unresolved_no_expert rather than hanging forever.

Observability — the trace is half the demo

You do not debug an agent by reading its output. You debug it by replaying its decisions, because every interesting failure is in the middle steps.

In the reference

Every model call carries a span tagged with run id and record version, so the gate loop appears as three sibling spans with visible diffs. Show that on stage, not just the finished brief.

TIER 3

What makes it handoff-ready

The last three hours, and the tier that answers "could someone else pick this up and keep building?" — which is a question you will be asked.

Orchestration in code, judgment in the model

Use the model for judgment inside a step. Use deterministic code for sequencing between steps. An LLM choosing its own next action is unbounded in cost and unauditable after the fact.

In the reference

Faculty returns a verdict; Python decides that a block means revise and that three blocks mean escalate. The model never gets to say "let me try that again."

At least one assertion a human is not making by eye

Without it, "we improved the prompt" is an unfalsifiable claim — a delicious irony in a system built to test falsifiable claims.

In the reference

One golden case whose real-world outcome is known, plus five assertions: the gate blocks a thesis with no falsifiable claim; every evidence row carries a source id; no run exceeds its token ceiling.

A defined failure behaviour per dependency

Every external thing you depend on will fail during the 48 hours. Decide in advance what happens, or discover it live in front of judges.

In the reference

Model API down → named fallback model. Corpus returns nothing → say so rather than invent. Expert does not answer → marked unknown and the run continues.

The translation

Same skeleton, thinner muscle

This is the argument worth making out loud: nothing on this list is an enterprise luxury you are being asked to skip. Every principle survives the 48-hour cut at reduced fidelity, and the entire skeleton is about 250 lines of infrastructure code — less than most teams will spend on prompts.

Five anti-patterns

The manager agent

An LLM that decides which agent runs next. Feels sophisticated, is unbounded in cost, and cannot be debugged — because the control flow is different every run.

Conversation as state

Keeping the run's memory in the message history. Works until the first restart, the first context overflow, or the first time someone asks what happened at step four.

Prose between agents

Agent A writes a paragraph, agent B interprets it. Two lossy translations per hop, and no boundary at which a malformed handoff can be caught.

Persona count as a proxy

Five characters in the cast is not five times as agentic. The measure is state transitions and tool calls, not how many system prompts wear a costume.

Framework before state model

In 48 hours an orchestration framework costs more to learn than the hundred lines it replaces, and it hides the state model you most need to think about. Write the loop by hand; adopt a framework on day three of a project, not hour three.

Scoping

Build in this order

The order is not arbitrary — each tier is load-bearing for the next. A team that spends hour one on prompts and hour thirty on state will rewrite everything; a team that spends hour one on the record will not.

H0–H2The spine. Record table, typed models, one hard-coded happy path end to end with a stub model. No prompts yet.Tier 1
H2–H4Real model calls. Swap the stub for the router. Add the attempt counter and the token ceiling before the first loop exists, not after it runs away.Tier 1
H4–H6Retrieval and provenance. Ingest the corpus, wire search, make every claim carry a source id from the first line you write.Tier 2
H6–H8The human callback and tracing. Suspend, resume, timeout. Then the trace decorator — which is also how you debug everything after this point.Tier 2
H8+Assertions, fallbacks, and the demo. The golden case, the five checks, the failure behaviours. Then real users — and remember you owe three walkthroughs, a recorded stress test, and a fix commit.Tier 3

The remaining time is not build time. It is the iteration you will be judged on — three fellow students through the flow, one classmate deliberately trying to break it, and a commit that fixes what they broke. Teams that treat hour 24 as a deadline for features rather than for feedback consistently ship the least convincing demos.
